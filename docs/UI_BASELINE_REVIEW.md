# UI 시안(`reference/design-ui`) 반영 내역

> 작성일: 2026-09-13
> 대상: `reference/design-ui` (4e95d8f, "참고용 UI 시안") vs. v4 제품/API 계약

`main`은 비어 있는 스캐폴드였고, 실제 화면은 `reference/design-ui` 브랜치에만 있었습니다.
그 브랜치는 머지 대상이 아니라고 명시돼 있어서, **디자인·문구·입력 UX는 그대로 가져오고
계약과 어긋나는 부분만 고쳐서** 이 브랜치에 구현했습니다.

---

## 1. 그대로 가져온 것

| 항목 | 이유 |
|---|---|
| `globals.css` 색 토큰 (navy 기본 / signal red 긴급 전용 / alert orange) | 용도가 고정돼 있어 긴급 신호가 묻히지 않습니다 |
| 480px 모바일 셸, 하단 고정 내비게이션, `nav-safe-area` | 1차 타깃이 스마트폰 단독 사용자입니다 |
| `regions.ts` 전국 시도·시군구 상수 | 외부 주소 API 의존이 없습니다 |
| 4단계 위저드 흐름 (사진 → 옷차림 → 예상 모습 → 전단 정보) | 기획서 3장 플로우와 일치합니다 |
| `ClothingField`의 3버튼 상태 선택, 브랜드 체크박스 토글 | "없음"·"모름" 같은 문자열이 AI 프롬프트로 넘어가는 것을 막습니다 |
| `AiPhoto`/`AiThumb` 라벨 강제 구조 | 우회 경로 없이 동결 항목을 지킬 수 있습니다 |
| 안내 문구 전반 (기억 안 나는 항목, 연락처 공개 확인, 자동 삭제) | 고령 보호자 기준으로 잘 다듬어져 있습니다 |
| 카카오 공유 → Web Share → 링크 복사 fallback | 키가 없어도 동작합니다 |

## 2. 계약에 맞춰 고친 것

### 2.1 20색 팔레트 (동결 항목 위반)

시안의 `lib/colors.ts`는 `coral`, `silver`를 가지고 있고 contract의 `denim`, `wine`이 빠져 있었습니다.
Backend의 `colorSchema`는 `contracts/colors.json`의 20개 id로 만든 `z.enum`이라,
그대로 보내면 `INVALID_INPUT`으로 거절됩니다.

→ 팔레트를 `lib/generated/colors.json`(= Integration `contracts/colors.json` 사본) 한 곳에서만 생성하도록 바꿨습니다.
스와치 hex도 contract의 rgb에서 계산합니다. 보기 좋으라고 다른 hex를 쓰면 사용자가 고른 색과
AI 프롬프트로 넘어가는 색 이름이 어긋납니다.

### 2.2 체형 값

시안 `BodyType = "slim" | "normal" | "heavy"` → 계약은 `"slim" | "average" | "heavy"` 입니다. `average`로 맞췄습니다.

### 2.3 appearance 필드명

시안은 `colorId`, 계약은 `color` 입니다. 소지품도 `{ type, color }` 입니다. 계약 이름으로 통일했습니다.

### 2.4 재생성 카운트

시안은 화면에서 `attempts`를 세고 첫 생성도 1회로 차감했습니다.
계약은 **첫 성공은 차감하지 않고 이후 3회**를 허용하며, **실패한 시도는 차감하지 않습니다.**
화면에서 세면 두 규칙 모두 어긋나므로, 서버가 주는 `regenerationsRemaining`만 표시합니다.

### 2.5 목격 장소 — 시안의 제안을 유지하되 스키마는 건드리지 않음

시안은 `place` 자유 텍스트를 `region { sido, sigungu }` + `placeDetail`로 분리하면서
"백엔드 스키마 변경이 필요하다"고 남겨 두었습니다.

분리 자체는 좋은 방향(지역별 집계 가능, 오타 없음)이라 **입력 UX는 그대로 두고**,
저장 직전에 `composePlace()`로 계약의 `place` 한 칸(최대 160자)에 합칩니다.
이어서 작성할 때는 `parsePlace()`로 다시 선택값으로 되돌립니다.

→ **Backend/DB 변경 없이** 시안의 이점을 가져갑니다. 나중에 지역별 집계가 필요해지면
그때 컬럼 분리를 제안하면 됩니다.

### 2.6 `수색중 / 발견 완료` 상태와 `markFound`

v4 데이터 모델에 해당 컬럼이 없고, 발행 후에는 삭제 외 변경이 막혀 있습니다(`CASE_PUBLISHED`).
→ 상태 배지를 Backend가 실제로 주는 값(`작성 중 / 생성 중 / 생성 실패 / 발행 전 / 발행됨`)으로 바꾸고
`수색 완료로 바꾸기` 버튼은 뺐습니다.

### 2.7 홈의 "최근 등록된 전단지" 목록과 알림 벨

공개 전단 목록을 주는 API가 없고, 전단은 noindex 비공개 링크 공유가 전제입니다.
남의 전단을 홈에 나열하면 기획서 12장 보안 원칙과 어긋납니다.
→ 목록을 빼고, 그 자리에 두 사진 모드 설명을 넣어 업로드 단계의 체크박스를 미리 이해시킵니다.
알림 벨은 로그인/로그아웃 버튼으로 바꿨습니다.

### 2.8 공개 전단 페이지

시안은 case 데이터를 받아 HTML로 전단을 다시 그렸습니다.
계약이 공개 경로로 주는 것은 `GET /api/flyer/[shareId]` PNG 하나입니다.
→ 그 PNG를 그대로 보여 줍니다. 같은 내용을 HTML로 한 번 더 그리면 전단 이미지와 화면 문구가 갈라집니다.
삭제·미발행 전단은 PNG가 404라 이미지 로드 실패로 판별해 "이미 내려간 전단입니다"를 보여 줍니다.

### 2.9 업로드 리사이즈

시안의 `resizeImage()`는 data URL을 돌려줬지만 `POST /api/cases`는 multipart `File`을 받습니다.
Backend 제한(4MB, jpeg/png/webp, 32~6000px)에 맞춰 `preparePhoto()`가 크기·품질을 단계적으로 낮춰
4MB 이하 JPEG `File`을 만들고, EXIF 회전은 `createImageBitmap(..., { imageOrientation: "from-image" })`으로 처리합니다.

### 2.10 자동 삭제 시간 표기

시안은 "48시간"으로 안내했지만 Backend의 cleanup cron은 **생성 24시간**이 지난 case를 지웁니다
(기획서의 "최대 48시간" 정책 안쪽 값). 화면 문구를 24시간으로 맞췄습니다.

## 3. 시안에 없어서 새로 만든 것

- **로그인/회원가입** — Supabase Auth Email/Password, `AuthProvider` + `RequireAuth`
- **실제 API 연동** — `lib/api/`, Bearer 토큰, ErrorCode → 한국어 안내 매핑
- **이어서 작성** — `/create?case=<id>`, 저장된 case를 입력 상태로 복원
- **불필요한 PATCH 차단** — 생성 입력이 실제로 바뀐 경우에만 전송해 결과 초기화를 막음
- **signed URL 만료 복구** — 이미지 로드 실패 시 case 재조회
- **색을 고르지 않은 `known` 항목 차단** — 계약상 `known`은 색이 필수
- **삭제 확인 다이얼로그** — 공유 링크가 즉시 닫힌다는 점을 명시

## 4. 팀에 확인이 필요한 것

### 4.1 공개 전단에서 전화 걸기 (Backend 요청)

지금 공개 전단은 PNG 한 장이라 전화번호가 **이미지 안에만** 있습니다.
번호를 눌러 바로 걸 수 없어서, 링크를 받은 이웃·상인이 번호를 손으로 옮겨 적어야 합니다.

→ `GET /api/flyer/[shareId]/meta` 처럼 **이미 PNG에 찍혀 있는 공개 필드만** 돌려주는 경로가 있으면
`tel:` 버튼을 붙일 수 있습니다. 새로 노출되는 정보는 없습니다.

```json
{ "name": "...", "age": 78, "heightCm": 152, "missingAt": "...", "place": "...",
  "contact": "010-...", "notes": "...", "appearance": { }, "label": "AI로 재현한 예상 모습" }
```

우선순위가 가장 높은 요청입니다. 결정 전까지는 PNG + 공유 버튼으로 동작합니다.

### 4.2 `missingAt` 형식

계약상 최대 80자 문자열입니다. Frontend는 `datetime-local` 값(`2026-09-13T10:00`)을 그대로 저장하고
전단 PNG에는 그 문자열이 그대로 찍힙니다. 사람이 읽기 좋은 형식(`2026년 9월 13일 오전 10:00`)으로
바꿔 찍을지, Frontend가 포맷해서 보낼지 정하면 됩니다.

### 4.3 자동 삭제 24시간 vs 48시간

기획서는 "최대 48시간", cleanup cron은 24시간입니다. 둘 중 하나로 문구와 구현을 맞추는 편이 좋습니다.

### 4.4 공개 전단 경로

`main` 스캐폴드의 `/c/[shareId]`를 유지했습니다. 시안은 `/flyer/[shareId]`였습니다.
바꾸려면 발행된 링크가 바뀌므로 제출 전에 정하는 편이 안전합니다.

## 5. 점검에서 추가로 잡은 것 (2026-09-13)

v4 P0 목록과 코드를 대조하면서 찾아 고친 항목입니다.

| 문제 | 조치 |
|---|---|
| `synthetic demo` 진입점 없음 (기획서 2.1 P0, 3장 플로우) | `/demo` 정적 페이지 추가. 홈에 "30초 만에 예시 전단 둘러보기" 복구 |
| `face_only` 인데 몸 정보가 빈 case 를 이어서 작성하면 generate 에서 `INVALID_INPUT` 을 맞고 되돌아갈 길이 없음 | `resumeStep()` 이 그 경우 사진 단계부터 재개 |
| 저장된 사진을 지워도 `다음` 이 눌려 사진 없이 진행됨 | 보이는 사진이 있을 때만 진행 |
| `다음`/`발행` 버튼이 아무 설명 없이 비활성화됨 | 부족한 항목 목록(`blockers`)을 버튼 위에 표시 |
| `Intl.DateTimeFormat("ko-KR")` 이 Node 에서 `AM`, 브라우저에서 `오전` 을 내놓아 hydration 오류 | `Intl` 제거, KST 고정 포맷터로 직접 출력 |
| 시간대 없는 `missingAt` 을 `new Date()` 가 실행 환경 로컬 시간으로 읽음 | 시간대가 없으면 `+09:00` 으로 고정 |

### 남은 권장 사항

4단계의 전단 정보는 **발행할 때 한 번에 저장**됩니다. 작성 중 탭이 죽으면 입력이 사라집니다.
고령 보호자가 급한 상황에서 앱을 오가는 것을 고려하면, 이름/시각/장소/연락처는 생성 입력이 아니라
PATCH 해도 결과가 초기화되지 않으므로 자동 저장을 붙일 수 있습니다. 팀 결정이 필요합니다.
